# QBR Dashboard: User-Testing Limitation

## Position

Representative-user testing was considered as part of the intended evaluation approach but could not be completed because access to suitable participants was not available within the project timeframe. No interviews, moderated tasks, usability timings, participant quotations, satisfaction ratings or user-acceptance results are therefore claimed.

This is a project limitation rather than evidence that the interface is fully usable. The target roles described in the portfolio, a QBR coordinator and a service or account reviewer, remain design assumptions based on the intended workflow. They have not been validated as research-backed personas.

## Why user testing would have been valuable

Testing with representative users would have provided evidence that technical checks cannot supply. It could have shown whether workplace terminology matched user expectations, whether participants understood upload and export scope, whether validation messages supported recovery, and whether reviewers interpreted RAG status and metric-separated charts correctly. Observing real tasks could also have revealed hesitation, wrong turns, accessibility barriers and missing information that are difficult to identify through developer inspection.

A small qualitative study with two or three relevant users would not have proved universal usability, but it would have strengthened the design process. Repeating a task after a feedback-led change would also have demonstrated that iteration was based on observed need rather than developer preference.

## Effect on the evidence

The portfolio does not claim:

- validated personas or target-audience needs;
- representative-user task success, efficiency or satisfaction;
- participant quotations, ratings or time savings;
- a feedback-led before-and-after design change;
- stakeholder user-acceptance or production sign-off.

The absence of these claims protects the validity of the submission. Invented participant evidence would be academically and professionally inappropriate.

## Alternative evaluation completed

The unavailable user evidence was not replaced with a false equivalent. Instead, the project records complementary technical and expert evidence:

- a heuristic review based on visibility, error prevention, consistency and recovery principles;
- four low-fidelity design states covering overview, validation, detail and mobile layouts;
- 20 passing automated regression tests;
- Chromium, Firefox and WebKit workflow checks;
- automated accessibility scans across four views and three engines;
- corrected text and toast contrast defects;
- keyboard checks for mobile navigation and the skip link;
- five performance runs using a 1,000-row fixture;
- explicit limits for genuine Safari, screen-reader and organisational approval.

This evidence demonstrates functional quality and a systematic evaluation process, but it does not establish user-centred validation. Heuristic evaluation is useful for identifying likely usability problems, while direct observation would have tested whether those assumptions matched real behaviour (Nielsen, 1994).

## How testing could have been conducted

If participant access had been available, the most proportionate method would have involved one QBR preparer and one QBR reviewer, with an optional participant who uses keyboard, zoom or assistive technology. They could have been asked to locate a template, import valid and invalid fixtures, identify an at-risk record, apply combined filters, explain a trend, export a report and clear disposable data. Results would have recorded task outcome, errors, help, time and confidence, followed by one prioritised change and a repeat of the affected task.

This proposed method is included only to demonstrate awareness of appropriate evaluation practice. It was not executed, and no results are implied.

## Conclusion

User testing would have improved confidence that the dashboard's terminology, workflow and presentation met genuine audience needs. Practical participant-access limitations prevented that stage from being completed. The project therefore relies on documented technical testing and expert evaluation, states the resulting evidence gap openly, and avoids any claim of representative-user validation.
